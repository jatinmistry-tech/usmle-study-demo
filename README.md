# USMLE Step 1 practice monorepo

A TypeScript/npm-workspaces application with React, Vite, Tailwind CSS, an Express backend-for-frontend (BFF), and an Express API using Prisma ORM with Neon PostgreSQL.

```text
apps/web/                 Practice interface
apps/bff/                 Browser-facing Express gateway
apps/api/src/             Express domain API + Prisma persistence
apps/api/prisma/          Schema, committed migrations, seed script
apps/api/prisma.config.ts Prisma CLI configuration
packages/shared/          Common TypeScript request/response types
.github/workflows/        GitHub Actions validation
render.yaml               Render Blueprint
```

Request flow: **web → BFF → API → Neon PostgreSQL**. The browser never receives database credentials or the service API key. The API returns answer keys and explanations only after submission.

## Frontend-only demo

To run React without backend services, set `VITE_USE_MOCK_DATA=true` in `apps/web/.env.local` (copy `apps/web/.env.example` on a fresh checkout), then run `npm run dev:web` from the root or `npm run dev` inside `apps/web`. Open <http://localhost:5173>. Mock mode includes catalog data, practice, bookmarks, history, and dashboard/performance statistics. See [frontend setup](apps/web/README.md). Server and Neon environment files do not need changes.

## Local setup

Use Node.js 24 (`.nvmrc`) and npm 10 or later. Run commands from the repository root.

```bash
nvm use
npm ci
npm run env:setup
npm run dev
```

Open <http://localhost:5173>. The BFF runs on port 4000 and the API on 4001. React calls `/bff` endpoints, and Vite proxies `/bff` to the BFF (with `/api` retained for compatibility). Environment changes require restarting the processes. Prisma Client is generated by the dev, build, typecheck, and test commands; generated code is ignored by Git. The Prisma CLI is a root development tool shared by the API scripts.

Without `DATABASE_URL`, the API uses the same fictional question fixtures and an in-memory attempt store. Data disappears on restart. With a database configured, questions and attempts come from Prisma; migrate and seed before starting the API.

`env:setup` creates a root `.env` with private file permissions and distinct random development service/admin keys. It preserves an existing file and never prints secrets. Add both Neon URLs to this file before following the database setup below. For manual setup, `cp .env.example .env` is also supported.

Leave `NODE_ENV` unset in the shared local `.env`; Vite selects the appropriate mode for dev and build. Setting it to `development` there also selects React's development bundle during a production build. Render injects `NODE_ENV=production` into its server services.

### Development and health commands

| Command | Purpose |
| --- | --- |
| `npm run dev` | Generate Prisma Client and run shared types, API, BFF, and Vite together |
| `npm run dev:servers` | Run API and BFF; start Vite separately with `npm run dev -w @usmle/web` |
| `npm run health` | Check running web HTML, API/BFF liveness, and end-to-end readiness |
| `npm run health:db` | Also require PostgreSQL mode and read the catalog through the BFF |
| `npm run test:integration` | Render React and exercise real BFF/API HTTP calls with embedded PostgreSQL |
| `npm run check` | Validate/generate Prisma, run ESLint, check TypeScript, test, and build every workspace |

Run health commands in a second terminal after starting the application. They exit nonzero on failure and never print response bodies or credentials. Health scripts use ports from the root `.env`; override `HEALTH_WEB_URL`, `HEALTH_BFF_URL`, or `HEALTH_API_URL` with HTTP(S) service origins for a different setup. The free-plan Render API uses a public HTTPS origin protected by the service key for application routes.

`/health` reports process liveness. API `/ready` tests database access; BFF `/ready` calls API readiness and reports `storage: postgresql` or `storage: memory`. Memory readiness means the limited practice demo is available, not the complete database-backed application. Render checks BFF `/ready` so upstream readiness failures also mark the BFF unavailable.

For a full local verification: configure Neon, run `db:migrate` and `db:seed`, start `npm run dev`, then run `npm run health:db`. In the browser, browse subjects/topics, submit a question, save a bookmark, refresh, and verify history, explanations, and performance. Keep the same browser storage/session during this check.

## Neon and Prisma

1. Create a Neon project and database.
2. In Neon’s **Connect** dialog, copy the **pooled** connection string to the root `.env` as `DATABASE_URL`.
3. Copy the **direct**, non-pooled connection string to `DIRECT_URL` for migrations and seeding. Keep the TLS parameters Neon supplies in both URLs.
4. Run:

```bash
npm run db:validate
npm run db:generate
npm run db:migrate
npm run db:seed
npm run dev
```

Example formats (placeholders, not credentials):

```dotenv
DATABASE_URL=postgresql://USER:PASSWORD@HOST-pooler.REGION.aws.neon.tech/neondb?sslmode=require
DIRECT_URL=postgresql://USER:PASSWORD@HOST.REGION.aws.neon.tech/neondb?sslmode=require
```

`db:migrate` runs **Prisma migrate deploy**, applying committed migrations without a shadow database. Use the command below when developing a new migration:

```bash
npm run db:migrate:dev -w @usmle/api -- --name your_change
```

Use a disposable development database for `migrate dev`; Prisma may request a reset and needs permission to create a shadow database. Never run it against production. The database command wrapper requires `DIRECT_URL`, while validation and client generation work without database credentials. The placeholder URL in `prisma.config.ts` is only for offline validation/generation. Seeds run explicitly, not automatically during deployment or migration.

The seed script upserts three subjects, three topics, three original fictional USMLE-style questions, and twelve answer options in a transaction. Stable UUIDs make reruns idempotent. It does not invent users, attempts, or bookmarks. Demonstration content requires editorial review before educational use. [Prisma PostgreSQL connection configuration](https://www.prisma.io/docs/orm/v7/core-concepts/supported-databases/postgresql) and [Neon connection documentation](https://neon.com/docs/connect/connect-from-any-app).

## Database model

Prisma uses singular model names and camelCase fields, mapped to the exact PostgreSQL table and column names supplied:

| Table | Columns |
| --- | --- |
| `Users` | `Id`, `Name`, `Email`, `CreatedDate` |
| `Subjects` | `Id`, `Name` |
| `Topics` | `Id`, `SubjectId`, `Name` |
| `Questions` | `Id`, `TopicId`, `QuestionText`, `Explanation`, `Difficulty`, `CreatedDate` |
| `QuestionOptions` | `Id`, `QuestionId`, `OptionText`, `IsCorrect` |
| `UserQuestionAttempts` | `Id`, `UserId`, `QuestionId`, `SelectedAnswer`, `IsCorrect`, `TimeTaken`, `AttemptedAt` |
| `Bookmarks` | `Id`, `UserId`, `QuestionId`, `CreatedAt` |

Every ID and foreign key uses PostgreSQL `uuid`; Prisma supplies UUID defaults. Dates use `timestamptz`, with creation timestamps defaulted by PostgreSQL. All specified fields are required. `Difficulty` is an enum (`EASY`, `MEDIUM`, `HARD`, default `MEDIUM`); `TimeTaken` is a nonnegative integer measured in seconds. The migration includes a CHECK constraint for `TimeTaken` that Prisma schema syntax does not represent.

`Topics.SubjectId` references `Subjects.Id`; `Questions.TopicId` references `Topics.Id`; options reference their question. Attempts reference a user, question, and selected option. The composite foreign key `(SelectedAnswer, QuestionId) → QuestionOptions.(Id, QuestionId)` ensures `SelectedAnswer` references an option's `Id` **and** prevents selecting an option belonging to another question. `IsCorrect` on an attempt is the server's grading snapshot.

Indexes cover topic/subject lookup, topic/difficulty filtering, question creation date, options by question, and user attempt history. Emails are unique, and bookmarks have a unique `(UserId, QuestionId)` constraint. User deletion cascades to attempts and bookmarks; content relationships restrict deletion to protect references. PostgreSQL names are case-sensitive because the migration uses quoted identifiers.

Content endpoints validate 2–8 options with exactly one correct answer. All question/option writes require the separate admin key. Questions with attempts are immutable; create a new question to revise recorded content. Direct database content writes must preserve the same answer-key rules. See [API endpoint documentation](apps/api/README.md).

The initial Prisma migration creates these seven tables. If the earlier starter's lowercase `attempts` table already exists, it remains untouched and is no longer used. Legacy session/slug records are not imported automatically because their IDs differ from the new UUID question and option IDs.

## Practice behavior

The browser stores an anonymous session UUID in local storage. The API creates a demo `Users` record with that UUID and a reserved `demo.invalid` email when the browser first submits an answer. This preserves the current anonymous interface; it is not account authentication.

Every submission creates a new `UserQuestionAttempts` record, including the selected option UUID and elapsed whole seconds. Progress displays the latest answer per question, so retries do not inflate the number of questions answered. Refreshing keeps database progress but restarts the visible block. Clearing browser storage creates a new session. Bookmark routes create, list, and delete bookmarks for the current session. Bookmark creation is idempotent. The React bookmark page supports revisiting and removing saved questions.

## Validation

```bash
npm run db:validate
npm run db:generate
npm run lint
npm run typecheck
npm test
npm run build
```

Tests exercise API grading, input validation, BFF forwarding, migration constraints, seed idempotency, and Prisma persistence against embedded PostgreSQL (PGlite). They run migration deployment and seeding twice to verify reruns, need temporary localhost sockets, and do not access Neon or require real credentials. Advisory locking is disabled only for the embedded test engine; Neon deployment retains the normal Prisma migration lock. The embedded database uses a single test connection; the production runtime pool is capped at five connections.

The full-stack test renders the actual React routes in a DOM and uses the browser client, BFF, REST API, Prisma, committed schema, and seed script without mocked HTTP responses. It verifies persisted grading, hidden answers, bookmarks, history/review, dashboard/statistics, CORS preflight, service authentication, and readiness failure propagation. This is automated DOM/HTTP integration, not a visual browser test or live Neon connectivity test. See [integration verification notes](docs/integration.md) for the checks performed and untested external steps.

GitHub Actions runs dependency installation, Prisma generation/validation, ESLint, TypeScript checks, tests, and production builds on pull requests and pushes to `main`. Render tracks `main` and auto-deploys after checks pass. See [the complete CI/CD workflow](docs/ci-cd.md) for GitHub branch rules, Render integration settings, and release verification. The REST suite also covers CRUD, admin protection, learner ownership, answer hiding, statistics, and error handling. Root npm overrides select patched `deepmerge-ts` and `mysql2` versions for Prisma tooling; recheck their compatibility and advisories when upgrading Prisma. After building:

```bash
npm run start -w @usmle/api
npm run start -w @usmle/bff
```

Serve `apps/web/dist` as a static website. For `npm run preview -w @usmle/web`, build with `VITE_BFF_URL=http://localhost:4000` and start the BFF with `WEB_ORIGIN=http://localhost:4173`.

## GitHub and Render

The root `render.yaml` creates a free React static site, a free BFF web service, and a free REST API web service. Neon hosts PostgreSQL. See [Render deployment steps](docs/render-deployment.md) for GitHub setup, Neon credentials, build/start commands, CORS, URL references, migrations, seeding, health checks, and SPA verification.

Builds run from the repository root. The BFF uses the API's public HTTPS URL because free Render services cannot receive private-network traffic. Service/admin keys protect API requests; the browser receives neither key. The API build applies committed migrations because pre-deploy commands require paid compute. Seed explicitly from a trusted local environment. [Render free plans](https://render.com/docs/free), [deployment commands](https://render.com/docs/deploys).

During initial Blueprint creation, supply API `DATABASE_URL`/`DIRECT_URL` and BFF `WEB_ORIGIN`. Render generates distinct API/admin secrets, shares only the service key with the BFF, and references assigned HTTPS URLs for `API_BASE_URL` and `VITE_BFF_URL`. Update `WEB_ORIGIN` to the actual React origin after provisioning; rebuild the static site when its BFF origin changes. Free services can cold-start, and the two Node services share the workspace's free-hours allowance. No account provisioning or live deployment has been performed.

## Secure environment configuration

Store local secrets only in the ignored root `.env`. Use Render's API service environment for production database credentials. Injected platform environment variables take precedence over the local file. `.env.example` contains no real secrets; neither database URL should ever use a `VITE_` prefix or be set on the web service. Avoid printing connection strings or committing exported database credentials.

| Variable | Consumer | Description |
| --- | --- | --- |
| `NODE_ENV` | Servers | `production` on Render |
| `API_PORT` | API | Local port, default `4001` |
| `BFF_PORT` | BFF / Vite proxy | Local port, default `4000` |
| `PORT` | Each server | Render port; overrides the local setting |
| `API_BASE_URL` | BFF | REST API origin, or a Render private hostport reference |
| `API_TIMEOUT_MS` | BFF | Upstream deadline including response body; default 8000 |
| `API_KEY` | API + BFF | Matching service secret; required in production |
| `API_ADMIN_KEY` | API / trusted admin client | Distinct content-administration secret; required in production |
| `WEB_ORIGIN` | BFF | Allowed browser origin; required in production |
| `DATABASE_URL` | API | Pooled PostgreSQL runtime connection; required in production |
| `DIRECT_URL` | Prisma CLI / seed | Direct connection for migrations and seeds |
| `VITE_BFF_URL` | Web build | Public BFF URL; blank uses the local Vite proxy |

## HTTP contracts

Include a UUID v4 `x-session-id` header for progress and submissions. The BFF attaches the private API key.

| Method | Route | Behavior |
| --- | --- | --- |
| GET | `/health` | Server liveness |
| GET | `/ready` | Database readiness; 503 if unreachable |
| GET/POST/PUT/PATCH/DELETE | `/api/subjects`, `/api/subjects/:id` | Subject CRUD |
| GET/POST/PUT/PATCH/DELETE | `/api/topics`, `/api/topics/:id` | Topic CRUD |
| GET/POST/PUT/PATCH/DELETE | `/api/questions`, `/api/questions/:id` | Question CRUD; responses omit answers |
| GET/POST/PUT | `/api/questions/:questionId/options` | Read, add, or replace options |
| GET/PATCH/DELETE | `/api/questions/:questionId/options/:id` | Individual option operations |
| GET | `/api/attempts`, `/api/attempts/:id` | Current session attempt history |
| GET/POST/DELETE | `/api/bookmarks`, `/api/bookmarks/:id` | Current session bookmarks |
| GET | `/api/statistics` | Current session totals, accuracy, timing, and subject/topic breakdown |
| GET | `/api/questions` | Question fields and option UUIDs; no answer keys |
| POST | `/api/answers` | `{ "questionId": "QUESTION_UUID", "optionId": "OPTION_UUID", "timeTaken": 17 }`; grades and records an attempt |
| GET | `/api/progress` | Answered, correct, and accuracy for the session's latest answers |

`timeTaken` defaults to zero for older clients. Database readiness is checked at startup and by `/ready`; `/health` checks process liveness. Content mutations require `x-admin-key` in addition to the service key. All request bodies, resource IDs, and REST query parameters are validated with Zod. Production requires distinct service/admin keys. The BFF exposes read-only subjects/topics/questions, answer submissions, own attempts/bookmarks, and dashboard composition under `/bff`; content administration remains on the REST API behind its separate admin key. Its default eight-second upstream deadline includes body reading, and service credentials stay server-side. See [BFF endpoints and configuration](apps/bff/README.md).

This remains an anonymous demo without account authentication, user record authorization, or rate limiting. Replace the session-to-user bridge with authenticated user identity before exposing personal records. USMLE and NBME are not affiliated with this project.

Browser endpoints are documented in [apps/bff/README.md](apps/bff/README.md). Set `API_BASE_URL` when configuring the BFF; it replaces the earlier `API_URL`/`API_HOSTPORT` settings. The free-plan Render Blueprint uses public HTTPS service URLs; private hostport references remain supported for paid-service configurations.

The [React frontend](apps/web/README.md) now provides dashboard, subjects, topics, practice, explanations, bookmarks, history, and performance pages with React Router. Browser calls use only VITE_BFF_URL. For all pages, configure Neon, apply migrations, and run the seed script.
